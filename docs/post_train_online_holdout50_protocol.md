# 新城市线上闭环留出评测协议

## 目标与冻结规则

使用同一套当前生产提示词、TravelRoute Schema、线上 LangGraph 审核及返工逻辑，比较 Base、v2/A/B-SFT、v2/A/B-DPO 共七组。每组 50 题 × 3 生成种子 × 2 模式，共 300 次任务，全部 2,100 次；不是三次独立训练。

数据目录：`data/post_train/online_holdout50_20261027_v2`。`cases.json` 保存完整输入、评分规则与可行性证据；`case_catalog.json` 提供逐题请求；`FROZEN.json` 固定文件和执行代码哈希。评分器与证据路线不传给模型或 Reviewer。冻结后不得根据任何模型表现删题、换题或改规则。

v1 为作者阶段与 Mock 流程记录，未做真实模型评测；v2 改为使用真实生产 API 适配器调用审核角色。最终结果只读取 v2/matrix，不能混用历史测试结果。

## 数据设计

城市为北京、天津、杭州、绍兴、无锡、合肥、武汉、长沙、洛阳、福州，每城 5 题。它们不属于此前主要对照的南京、上海、三亚、成都、苏州、丽江、景德镇七城。脚本另检查指定历史发布数据的消息精确重合；该检查不等于证明与全部历史语料不存在语义重合。

|每城题号|目的与用户情境|主要检查|
|---|---|---|
|01|老人/孩子慢节奏，偏好某类景点|最多数量、最低停留、类别偏好、避免凑点|
|02|用户把原先每日 3 点修改为 2 点，含必去和排除|新指令优先、严格晚于 10 点、必去/禁去、入场窗口|
|03|2 或 3 天，不同天不同点数，中午休息|不平均摊点、全程去重、停留时长、交通与午休冲突|
|04|按城市轮换 38°C、37.9°C、阵雨、紧下午窗口|高温边界、未知不当室内、避免擅加禁令、雨具提醒、通勤与开放窗口|
|05|一半城市仅有 3 候选但 3 天每天 1 点可行；另一半候选充足但必去点需 90 分钟、用户仅有 60 分钟|少候选不应全拒、无解必须有解释、不允许假交付|

分层为 40 常规 + 10 困难；可行性为 45 可行 + 5 确定无解。45 题有 18–20 个候选，只有专门的 5 题候选稀疏。这里“常规”指前置条件现实充分，仍含明确约束，不代表简单题。

196 个保留景点取自本次高德查询，保存原始记录、AMap ID、开放窗口来源与方向道路回放。已筛除暂停开放、明显商铺及部分重复子景点；不声称人工核实了所有场馆未来营业状态。道路资产保留早期抓取但最终未选用的边，不能把地图边总数当作最终候选数。

天气、日期、用户请求是显式构造的场景；景点和道路来自冻结查询。室内信息缺乏可靠证据时统一为未知，不按名称编造标签。当前软评分覆盖有类别证据的偏好和雨天提醒；没有真实台阶/强度标签，不能声称验证了老人登阶的全部能力。每个可行题有通过规则的见证路线；无解题有时间容量矛盾证明，另有负对照测试评分器。

## 与线上一致的执行边界

- Planner-Only：直接调用真实 Joint Planner 一次，生产解析、归一化照常执行，无审核返工。
- Online-Rework：直接运行 `app/planning/graph.py` 的生产 `build_graph()`，保留真实道路检查、Risk Gate、Reviewer、time_check、修正及最终安全门控。
- Reviewer 和 time_check 固定为现有线上 API 配置，当前解析模型为 `gpt-6.1-sol`；使用 `app/llm/openai.py` 的生产适配器、Responses 开关、reasoning effort 和重试配置。七组只替换 Planner。
- Reviewer 返工传入生产自然语言意见及上一版路线；时间返工使用生产 Day/景点/问题描述，禁止替换成独立评分器的错误码。主审核和时间核查分别最多 3 轮，按生产图转移执行，不简化为统一 3 次调用。
- 不修改生产硬规则来迎合测试。道路跨度可能触发线上保守拒绝；独立评分器判可行而系统拒绝时单列分析。
- 上游意图解析、候选检索和天气结果冻结；使用真实生产道路检查器，但道路请求由离线资产应答。餐馆、酒店、票价、景点攻略网络增强不在本次范围。因此是线上规划审核后半段复现，不是全链路在线搜索评测，也不是 Supervisor 引擎评测。

## 模型与推理绑定

|组别|加载方式|
|---|---|
|Base|原始 Qwen2.5-7B-Instruct BF16|
|v2-SFT|已有合并 v2-current BF16 权重|
|A-SFT|合并 v2 + 原 A SFT LoRA|
|B-SFT|原 Base + 原 B SFT LoRA|
|v2-DPO|合并 v2 + v2 DPO LoRA|
|A-DPO|先把 v2+A-SFT 合并为 BF16 临时父模型，再挂 A-DPO LoRA|
|B-DPO|先把 Base+B-SFT 合并为 BF16 临时父模型，再挂 B-DPO LoRA|

不使用此前准备的代数拼接 LoRA 工具替代正式父模型，避免与逐阶段 BF16 合并产生差异。顺序加载七组，GPU0、vLLM context 8192、BF16、eager、显存比例 0.90、关闭前缀缓存；Planner 温度沿用生产 0.3，最大输出 2048，top_p 使用 vLLM 默认值（未显式配置）。种子 42/43/44 控制 Planner 采样；线上审核温度为 0，Responses 不注入 seed，不能承诺审核绝对确定。任务顺序固定打散，并发 2。

## 指标与归因

|指标|含义|
|---|---|
|可行任务成功率|135 次可行任务中，解析成功且符合硬规则；闭环还须线上批准|
|正确拒绝率|15 次无解任务中，空路线和说明正确；闭环不得错误批准|
|结果正确率|上述两类合计，不能解释成全部交付了路线|
|JSON 解析成功率|最后一次 Planner 输出解析成功；不允许用旧合法输出掩盖最后返工失败|
|硬错误分布|候选越界、数量、去重、必去/排除、时间与通勤、开放窗口等，按题独立评分|
|软满足率|只对具有 soft_rubric 的题计算；与硬规则通过率分开|
|解释一致性、误放行、可行题误拒绝|区分答案错误与系统过度保守；解释关键词只是自动代理|
|三种子稳定性|每题 0/1/2/3 次通过分布，不把相关的 150 次视为独立城市样本|
|成本|角色调用数、真实输入/输出/总 Token、每个正确任务 Token、平均输出字符|
|响应时间|平均与 P50/P95 任务耗时、平均返工次数；并发与固定审核开销一并说明|

对 Base 的正确率差使用按城市成簇的配对 Bootstrap（3000 次），保留同题三种子，10 城市样本仍小，不据此强称显著。评分汇总输出 `docs/post_train_online_holdout50_report.md`，保留原始输出、失败响应、messages、图事件和调用 usage 供复核。

## 执行、费用与关闭服务

构造时只通过 `--capture` 请求高德；现有事实已捕获，正式评测不再请求高德或教师生成标准答案。生产 API 兼容探针在旧开发案例上完成，两次审核调用共 15,143 Token（单独保存，不计入正式成绩）。完整评测的 API 用量取决于风险门控和返工次数，不能拿探针精确外推；SDK 内部重试如未返回 usage，账本也无法恢复那部分计费，最终以供应商账单为准。

执行顺序：冻结 → Mock 全流程 300 次 → pytest → GPU0 空闲后顺序跑七组 → 每组汇总 → 自动关闭本任务启动的 vLLM。GPU0 或 8000 端口被其他任务占用时只等待，不杀其他服务。进度路径为 v2/matrix/status.json，各组还有任务级 status.json。正式运行耗时估计需取首组实际吞吐；等待其他任务的时间无法据此预估。

这是前瞻的新城市留出集，但设计参考了以往失败类型，不能宣称完全盲测。一旦据结果继续补 SFT/DPO，这套集应转为开发集，最终泛化结论需再留新的未参与调参样本。
