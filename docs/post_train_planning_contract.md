# 联合规划统一约束与重复开发集实验

版本：planner-contract-v1，2026-10-24。

## 生产协议

- 室内字段仍为 `pois[].indoor`：true 为输入明确室内，false 为明确室外，null 为未知或混合。提示词展示属性、来源、适用范围。既有快照标签只称“输入快照声明（未独立核实）”，不能冒称官方认证。
- 高德名称/类别推断保留为 `indoor_hint`，其来源为 `indoor_hint_source`；正式 `indoor` 为 null，不允许模型自己猜一个标签再给自己验收。新获取的候选仅凭博物馆名称无法满足“确认室内”覆盖，需要带范围的证据补充。仅展厅的证据不能推及庭院、排队或交通。
- 数量有效上限为系统 `max_per_day` 与用户明确每天上限中的较小值。本轮 `modification_notes` 中明确的新数量替代原始 query 数量；原始用户要求优先于改写/历史。只识别明确数量语法，不把全程数量或每点分钟数当作每天上限。恰好数量与上限不同，不可为了凑数重复或编造；冲突须说明不可行。
- 高温政策：已知当日最高温 >=38°C，11:00–15:00 与景点时间块有交集时，仅允许明确室内。11:00 恰好结束、15:00 恰好开始均允许。按出发日期对齐当日预报；没有出发日期时按预报顺序；用户明确模拟 >=38°C 为所有旅行日保守触发。缺失天气不等于安全，用户更严格限制仍需遵守。
- 该 38°C / 11–15 点界限是本项目明确采用的业务规则，不声称医疗安全保证。提示词与本地门控共用同一判定函数。
- 新规则会让旧“软高温挑战”成为确定性风险；对应预期标签已同步。室内仅名称搜索的覆盖测试应返回不足，不能为维持旧通过率虚报覆盖。

## 完整开发集重复对照

固定原始开发集 30 个状态，不取旧答案作示范。每个状态重新捕获新生产 messages，v1/v2 使用完全一致输入、Schema、temperature=0.3、max_tokens=2048，种子42/43/44。总计180次服务器本地推理，付费API调用为0；GPU0，两并发，完成后恢复原生Qwen服务。

记录每条完整请求、原始回答、停止原因、解析、规则错误、解释审计、耗时及token。优先报告每个种子30例通过数、每例0–3次成功、三次全过的稳健案例数、解析/截断、硬约束分项及规则与解释联合通过。不同种子是重复生成，不能把90次当作90个独立问题，也不能用该开发集宣称独立泛化。

本轮协议改变了提示词与门控，不能把新结果直接拼接到旧18/30与17/30称为模型提升。四组最终比较仍须在冻结独立测试上使用统一协议，API组也需按新协议重新记录，旧API记录保留作为历史实验。

目录：`data/post_train/sft_contract_eval_v1/`，binding保存生产代码、输入、Schema及回放哈希。断点只续跑相同协议。

## 定向小补数

32例：稀疏候选8、多日去重8、天气边界8、解释一致性8；只使用成都/苏州既有固定候选、道路及开放证据，不新增地图调用，不接触丽江/景德镇封存测试。

稀疏集合用2候选覆盖2天；多日用3候选覆盖3天，系统默认每天3点与用户每天1点并存，要求不填满、不重复。天气覆盖37.9与38°C、已知展厅与未知属性，以及11点结束/15点开始边界。解释集有两点道路转场，检查明确点数、停留分钟数与选点引用。

所有输入先通过独立离线可行解枚举及道路/开放审计；可行解不发送给教师。实际新生产messages在LLM边界捕获；教师gpt-6.1-sol，首轮本地规则+解释检查，最多1轮返工，不使用Reviewer。当前补数运行上限48次付费调用（旧版本试跑另计入全局上限），历史试跑与中断started也进入全局1000上限；不为达标凑条数。

首轮试跑发现室内证据来源被误当作知识库source_ids，暂停版本1并保留失败账本。版本2采用紧凑中文属性来源，并明确无知识库source时source_ids=[]。端点试跑又确认“后/前”严格语义导致60分钟窗口不可行，版本3将天气边界查询明确为不早于/不晚于且允许端点；与版本2输入messages完全相同的9条已通过数据复用，不重复付费。天气查询变化的样本重新生成，旧拒排不算模型错误。证据原始文件和哈希继续保存，不能把来源字符串当知识引用。

合格样本要再检查Qwen实际训练token长度<=3584，无截断；逐条审阅解释，不把规则通过当作语义全面认证。新数据独立导出，不自动启动SFT或DPO。

## 已知旧样本清理与版本纪律

`synth-0127` 的“本轮将原先集中在前两天……”是已确认的首轮答案返工叙述泄漏，加入针对性检测，并从新清理副本排除。不能把普通“改为留空用餐”一刀切误判。

release_v1/release_v2及旧权重不修改。清理副本249条仍保留其历史messages，不声称它们与新生产prompt一致。后续若要做新协议SFT版本，需要单独审计每条旧答案在新输入下仍成立、捕获新输入并记录迁移来源，不能静默换Prompt后声称是原始教师调用。

## 验证与下一步

基线573 passed；实现后最终589 passed（3条原有依赖警告），包含新增补数证据测试。重点边界：三值、名称不认证、数量修改优先、38/37.9、按日预报、11/15端点、返工泄漏及合法改写。

先完成重复对照与补数审计，再依据稳定失败类型决定新SFT；不自动DPO。若跨种子差异仍大，应报告不确定性，不据一次通过率选模型。价值指标是首轮可交付成功率、同例多次稳定成功、道路与开放合规、未知属性误当室内率、全程重复率、显式数量遵从、解释与路线一致率；解析率仅是最低门槛。
