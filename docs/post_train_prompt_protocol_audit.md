# SFT 全版本训练与评测提示词审计

审计日期：2026-10-25。只读取训练导出数据、账本、服务器副本、冻结案例和1200条实际请求；没有调用付费API、修改冻结资产、重训或切换模型。

## 结论

训练协议并没有保持跨版本一致。统一评测请求对所有模型一致，但不等于各模型训练、评测、当前生产三者一致。

|---|---:|---|---|---|
|Base|不适用|没有本项目SFT|不适用|仅作为统一请求下的原生基线|
|v1|156|旧版|旧版：未加入统一室内三值/高温/数量优先级协议|否，用户侧协议变化|

本次冻结评测使用：旧版系统提示词 + 新版用户约束协议。
当前代码生产使用：新版系统提示词 + 新版用户约束协议。

“一致”指固定指令、模板和约束定义；训练题与评测题的用户需求、景点、天气应当不同。表中没有声称训练案例与评测案例全文相同，也没有完成历史JSON Schema与tokenizer模板的逐版本追溯。

## 核验依据

- 所有7个训练集逐条扫描，共1501条。每版内部系统提示词均只有一种。v1/v2/v3/mc/v4-clean/v4共1347条为旧版；v2-large154条为新版。
- 旧系统提示词SHA256：`123e43ffa9d5f43ddffc05b753b754afe0fdaee68c20c52d1740a57dab59636b`。
- 新系统提示词SHA256：`402a279c8e218de671211b5c820b88d6cedb181beea8fd92bb7aef2fe4e35c2c`。
- 各训练集导出的输入messages均能在对应账本找到，说明不是导出时另改提示词，而是捕获的生产提示词版本发生了变化。
- 用当前生产捕获函数对原训练状态重构：v3/mc/v4-clean/v4的用户文本逐条完全匹配；其系统提示词不同。v2-large154条完整messages全部匹配当前生产。v1/v2用户文本亦不匹配当前生产。
- 50个冻结案例的用户文本全部与当前生产重构匹配；系统文本全部为旧版。
- 8组各150条实际评测请求，共1200条，messages全部与相应冻结案例一致。去除model字段后，各组请求哈希多重集合完全一致，包含seed、temperature、max_tokens、response_format。没有单独给某个版本删减提示词。
- 服务器上7份SFT数据及7份dataset_info与本地SHA256全部一致。这核验的是现存服务器副本，不替代训练启动时不可变快照或模型权重溯源。

## 具体变化

### 旧用户协议到新用户协议

增加明确的室内true/false/unknown解释及候选属性证据、每日数量上限和当前修改优先级、最高温>=38°C时11:00–15:00边界、解释与最终行程一致性要求。v1/v2训练时没有这些固定协议，本次评测有。

### 旧系统提示词到新系统提示词

新生产系统提示词增加：只输出JSON、不调用工具、顶层及嵌套字段范围、period枚举、HH:MM不能带日期、检索引用限制、空餐馆处理、解释长度建议及事实边界。该要求属于当前 `app/planning/prompts.py` 的生产提示词，不能简单称为仅教师私有提示词；问题是评测快照没有同步版本。

## 对已有结果的解释

原始结果可描述“不同历史训练版本在同一冻结请求下的表现”，但不能解释为“完全排除提示词因素后，数据量或候选池变化的单变量收益”。尤其不能据此认定扩充候选池本身导致v2-large退步。

前次说“训练额外加提示词”不够准确：新提示词确实进入了当前生产代码；更准确的问题是生产、训练和冻结评测没有绑定同一协议版本。

## 后续处理原则

1. 保留历史训练集、冻结评测和原分数，不覆盖旧文件。
2. 明确选定一个生产协议版本，训练、评测、部署绑定同一版本及Schema/聊天模板。不要为某个模型单独加提示词。
3. 可以把全部现有模型放在同一最新生产协议下补测，但需标注旧模型存在协议迁移；这不能追溯改变它们的训练输入。
4. 若要严格比较“只扩充训练候选池”的收益，必须用同一固定协议重新构造对照训练输入，检查答案兼容性，并控制基座、样本选择和训练预算。不能仅改JSON文件就声称旧权重已迁移。
