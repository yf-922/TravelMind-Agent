# 后训练数据质量与四组对照协议

## 2026-10-24 成本与范围调整（覆盖原800状态目标）

用户明确餐馆不纳入本轮，优先多约束难例与独立测试。已停止广泛裂变，保留原始结果；候选数据按城市/天数/天气/偏好分层限额，优先保留天然修复与同日多景点路线。当前155条精筛候选进一步选择135条；不为凑800继续生成。选择结果是中间快照，训练前仍须人工抽查与最终冻结。

已准备60个多约束补充输入，每个都有现存路线作为代码验证的可行性见证。见证不代表新输入已经调用过API，不直接冒充真实消息捕获样本。补跑最多90次（60首轮、最多30返工），仍在原1000次总预算内，预计新增约25万至45万Token，以实测为准；不足时先报告而不扩预算。

已冻结丽江/景德镇24个城市留出测试候选，禁止进入后训练。两地的当前道路回放缺失，且案例尚待可行性复核，因此暂不可执行或声称独立测试完成。保留固定输入与哈希，先补证据再跑四组。额外资产采集不默认授权付费外部请求；不造道路耗时，不用直线距离替代。留出指本轮后训练数据隔离，无法声称基础模型预训练从未见过这些城市。

API原60例基线继续保存，作为同源诊断。新增城市留出API首轮预留24次，预计约10万Token；完整返工与其他组的实际预算和耗时分开统计。原广泛合成的预计380万至420万Token不再适用于精简方案。

## 实验目的与边界

训练对象仅为 Joint Planner。比较 Base Qwen2.5-7B、SFT、SFT+DPO、在线 API teacher 四组，每组分别报告 Planner-Only 和 Rules+Rework（最多三轮返工）。模型、调用协议、案例、规则版本与原始输入均留档。先回答“首轮能否生成可执行规划”，再回答“加入同样的规则返工后是否减少调用和耗时”。Teacher 生成数据的通过率不能替代 Teacher 的测试集成绩。

60 个现有案例实际上共享少数城市候选池，不是 60 个独立城市。800 个裂变状态也不等于 800 份独立世界知识。候选中的室内标签部分来自高德类别推断，不能当作人工核验事实。原母本不含完整餐馆资产时，不编造餐馆，更不能宣称餐馆规划能力已训练充分。

## 当前生成与预算

- 本机通过 API 合成，无需 GPU，使用已有离线地图。训练与本地模型推理仍使用服务器 GPU0。
- 800 个状态，合成 939 次调用上限，API Planner-Only 60 次上限，真实预检 1 次，共不超过 1000 次。并发 8、超时 90 秒、客户端重试 0。已发起但未返回的请求也占预算。
- 候选池为空的场景记录为不可行，不花 Token 请求虚构正解。无法解决、超时、解析错误不伪装成通过。
- 消息通过生产 Joint Planner 的 invoke_fn 边界直接捕获；原始 messages、结构化 Schema、完整响应、模型返回标识、用量与延迟保存在 calls.jsonl。账本不含 API Key。
- 首轮通过才收录为正例；首轮失败至多一次规则返工。通过样本须同时通过生产风险规则、离线道路证据检查和显式偏好检查；未经归一化的原始输出先受检，防止去重或名称修正掩盖问题。

## 正例放行条件

1. TravelRoute Pydantic 可解析，天数/日期一致，每天非空，无全程重复、候选越界或虚构餐馆。
2. 开放时间、游玩时段、相邻路线耗时和步行上限满足可观测约束。缺失道路证据记为未核验，不当作通过；规则对复杂开放时间的解析能力有限，须抽查，不能宣称完全解决节假日营业问题。
3. 显式要求可直接判定：必去/排除具体地点、每天最多两个、每个至少90分钟、10点后出发、雨天室内、高温11至15点避免非室内活动。高温规则是保守操作性定义，非医学结论。没有台阶强度或商业街标签，不虚构对应标签或声称验证。
4. 消息去重；分城市/天气/天数/偏好/失败类型统计。报告多景点比例与被规则拒绝比例，防止大量“每天一个景点”的简单样本冒充复杂规划能力。
5. 成功样本没有达到目标数量时，报告实际有效规模，不降低质量阈值、不用 mock 补数量。

## DPO 偏好对与说服力

天然失败后修复的偏好对单列；人工缺陷对单列。两者始终共享原首轮输入。人工负例必须 Schema 合法，且实际运行检查后确认失败。不能拿格式破坏、随机打乱但仍合法的路线充数。

在线流水线的简单虚构地名/反向时间负例仅为保底原料。训练前须离线重建更有挑战的负例：优先选择真实但未在本次候选池中的同城地点、轻微通勤不足、开放窗口偏移、已知室外候选正午安排、漏掉明确必去点。逐对记录目标缺陷与检测证据，保留其余计划内容。导出时不可把这些简单保底原料直接等同于高质量 DPO 数据。

训练前按城市、天气、偏好、天然/人工负例抽取30对人工复核清单。检查正例是否合理、负例是否确实更差、解释是否与计划一致。该项尚未完成，不应写“人工验收已通过”。只有自动通过而未抽查的数据仍是候选数据。

## 测试隔离

现有60例与裂变训练数据同源，四组在这60例上的结果只能叫同源回放诊断。不得据此声称未知城市泛化。正式结论还需要在训练前冻结、从未进入合成或修复提示的独立测试集；优先新增候选池/城市/道路回放资产，另设组合约束挑战集。缺失的资产先列为待建，不能伪造已经独立留出。

训练验证按母本/候选池分组，先检查重叠再分割，不能随机拆分近重复裂变样本后称独立测试。当前仅三个主要城市时，按城市留出会显著缩小训练覆盖，应将此权衡单列，不能同时宣称“全部母本用于训练”和“这些母本完全留出”。

## 最终值得报告的指标

- 四组同输入的任务成功率、硬约束一次通过率、JSON解析率、越界率；失败与解析错误必须进入分母。
- 分天气/偏好类别的可观测软约束成功率，明确分母；无事实标签的能力标为未测。
- 完整闭环的最终成功率、返工轮数、无解时安全拒绝率、错误放行率。
- 首轮与闭环的端到端P50/P95耗时、输入/输出/总Token、每份成功规划调用数；付费代理金额未定价时只报用量，不猜费用。
- Base→SFT及SFT→DPO的同案例胜/负/平、成功率差值与配对bootstrap置信区间；样本少时同时给分子/分母。
- 天然偏好对与人工偏好对的独立偏好胜率、已知错误类型改善、与训练缺陷模板不同的挑战集表现。DPO若只学会拒绝显眼虚构地名，不算规划能力提升。
- 单卡训练显存峰值、吞吐、损失、样本截断率。3584 Token是否够用须按Qwen tokenizer测实际输入加输出；不允许静默截掉关键候选或答案。

## 执行阶段与预计时间

1. API与格式预检：已通过；正式生成启动后观察10分钟，监测超时、错误率、接受率、缺陷与落盘。稳定后停止人工轮询，后台继续。
2. 800状态生成及60例API基线：依实际单次耗时估算，一般几十分钟至数小时；每次调用可追溯。最终时间根据前10分钟实测更新。
3. 离线精筛、负例重建、Token长度检查、分组划分与抽查：约1至3小时，发现系统性错误则重新估算；此阶段不训练。
4. GPU0上SFT和4-bit DPO各16样本/5steps smoke：约10至30分钟含初始化。当前旧训练Shell/config仍需实机核验，不能宣称2分钟保证。
5. 正式SFT/合并/DPO/合并：以smoke吞吐推算，初步按数小时预算，未实测前不给精确承诺。
6. 四组固定协议评测、错误案例复盘和报告：约1至3小时或随API时延变化。API完整返工组、独立测试集、配对统计仍待执行；报告中的“待测”不得填成历史实验分数。
