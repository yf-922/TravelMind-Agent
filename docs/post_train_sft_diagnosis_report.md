# SFT-v2效果诊断：证据、原因与下一步（2026-10-24）

结论：现有证据不足以认定补充数据导致模型真实退化。最初固定30例开发集SFT-v1为18/30、v2为17/30，差一个案例；同请求重跑出现结果变化，排名反转。可以确认的是约束表达敏感、生产上下文缺失部分判分属性、解释与实际路线执行不一致，以及补充样本没有充分覆盖开发集的稀疏候选多日问题。不能把它简单归因为显存、训练没跑完、截断、或城市不够多。

## 实验设计和边界

完成135次本地vLLM调用，付费API调用0。Base、SFT-v1、SFT-v2各对同一15例开发案例运行3种输入：原始messages、仅重申规则、仅增加状态已有的室内属性。案例为原比较全部9个改善/退化项，加3个稳定通过、3个稳定失败。此为有选择偏差的机制诊断，不是30例总成绩，不是独立测试，不可把12/15写成模型最终80%成功率。丽江/景德镇测试未读取、未运行。

3组模型均temperature0.3、seed42、2048输出上限、相同TravelRoute JSON Schema、并发2，记录全部请求/响应、usage和失败。规则臂同时重申天数、全程唯一、用户更严格数量限制、开放和交通、解释一致、period格式和空餐馆；高温案例增加11–15时的明确化。它是一个规则组合干预，不能把收益全部归因某一条规则。室内属性臂只增加state.pois.indoor的三值信息，不推测标签、不提供见证路线或评分答案。原生产prompt未修改。

135份响应全部可由Pydantic读取，finish_reason均为stop，无输出长度截断；仍可能包含非法时钟导致本地评分失败，不能把“Schema可解析”等同业务合法。规则干预：v1改善5例、退化0；v2改善5例、退化2，净+3。补属性：v1改善2、退化1；v2改善1、退化1，净0。因此标签遗漏是实际问题，但单补标签不能解释或解决整体表现。

Base原始0/15主要受餐馆占位与period字符串影响。统一清空餐馆并按开始时刻归一period后的纯诊断为原始5/15、规则6/15、属性2/15；原始生产分数不被替换。SFT两版本在该格式诊断下分数不变。Base与SFT的原始分差包含格式学习，不能全部算规划能力提升。

## 1. 已证实：单次生成存在足以影响一两个案例的波动

原始输入15例与历史请求逐字段完全相等，每组15/15一致；但v1两例synth-0039、hard-022从通过变失败，选中子集从历史8/15变为6/15；v2两例synth-0212、synth-0027从失败变通过，选中子集从历史7/15变为9/15。不能用此定向子集推算全30新成绩，也不能宣称v2已优于v1；它说明原18→17不足以定因。

seed42并未保证服务跨次调用逐字相同；具体是采样、并发批处理数值差异还是其它推理非确定性，本轮没有隔离，不做猜测。后续比较需同一输入和种子集合的重复采样，或统一temperature0评估；temperature0也应检查重跑稳定性，而非承诺完全确定。

## 2. 已证实：约束执行对输入表达敏感

去重早已存在于全部250条训练messages，训练教师路线重复数为0；模型输出仍重复，并在reasoning中声称无重复。例如旧v2 hard-046把中山陵排两天，synth-0212把天涯海角和鹿回头重复安排。说明不是仅缺一句去重指令，也不是直接监督了重复路线。规则明确化可改善一部分，但v2仍出现1例重复，且雨天案例synth-0198在规则臂反而退化。不能认为追加一段prompt就彻底修复。

原开发评测解释矛盾如hard-022把玄武湖说成室内，synth-0039解释选3点但表格只有2点；本次有限解释检查也仍检出问题（原始v1为1/15，v2为3/15）。该检查只覆盖明确时长和选点引用等，不是完整语义正确率。

## 3. 已证实：模型看到的上下文与确定性判分依据存在缺口

30个开发状态都有已知indoor标签，但实际捕获的候选文本未输出这些类型化标签；规则却使用该字段判分。模型可能依赖名称/常识推断，而评分按固定标签执行。该固定标签本身也不是整座景区物理室内范围的全面认证（例如旧总统府标签不能自然推广到所有庭院）；后续要保留未知和参观范围/证据来源，不能为涨分随意改标签。

在15例中只补标签，v1高温错误4→2、v2 2→1，但整体收益有限，甚至有其它场景退化。说明需修复这个输入契约，同时不能把它当唯一根因。16/30开发输入同时出现用户最多2个与state.max_per_day=3；两者逻辑可按较严上限兼容，但存在表达层级不清晰，模型需自行取更严格值。诊断未单独干预此字段，尚无单因果效果估计。

## 4. 已证实分布差异，因果影响待控参验证：新城市不等于新增了所需难例

原156条训练：一日56、多日100；候选池主要3–4个。新增94条：一日71、多日23，候选池均7–8个，所有多日输入都有足够候选容纳每天2点。新增24条高温全部将11:00–15:00写进query，且全部候选室内属性未知；它们训练了保守时间避让，却没有新增“混合明确室内/室外属性下选点”的覆盖。雨天8条均限制为单个有证据的馆内展厅。

因此本轮新增虽有真实道路、可行性和较干净路线，却对“少候选分配到多天、宁可少排、不重复凑数”和原生产简短表达的覆盖不足。新增数据占37.6%行数、约35.1%助手目标Token；合并后1日占比35.9%→50.8%，但原多日样本绝对数量和每样本epochs并未减少，不能直接断言灾难性遗忘。

v1为30步、v2为48步，同为3epochs；混合数据同时改变优化步数和学习率采样轨迹。没有同等步数旧数据对照、仅定向旧城市难例对照，因此不能把变化单独归因城市新增、数据量、学习率或过拟合。验证loss持续下降到0.8798也无法证明规划质量上升或不存在遗忘。

## 5. 已确认但非v2特有：监督文本还有少量审计漏检

补查发现旧训练synth-0127提到“原先集中在前两天…调整为三天”，实际配的是无上一版路线的首轮输入。这条在v1、v2都存在。旧审计拦住了部分返工词，但漏了这种说法；这是实际监督噪声，应在新版本排除或重新生成独立首轮答案。本轮只记录，不改写已用过的训练快照。其它含“改为”记录经阅读是餐馆候选为空的处理，不一概认定泄漏。

无OOM、完整完成48步、训练最长2488低于3584、原新教师路线重复数均0，暂不支持训练中断、长度截断或直接学习重复标签是本次问题主因。

## 推荐的推进顺序

1. 先修复输入与评测契约并版本化：输出带证据/范围的室内三值属性，统一更严格数量上限；将11–15热区间明确为业务规则，不能让评测偷偷定义而用户只写“正午”。新prompt同时用于生产、捕获、数据和评测，旧结果保留，不能静默改写旧messages宣称字节一致。
2. 在原30例开发集统一协议复测v1/v2，至少3个共同种子，或temperature0并做重复稳定性检查。分开报告首轮结构、硬约束、软约束、解释一致、拒绝/空路线；不在这15例选中子集上选最终模型。预计准备与推理15–30分钟，0付费调用。
3. 数据先做零Token分类审计，移除已确认返工叙述泄漏。下一批如果需要合成，优先少候选/多日、同名不可重复、明确室内/室外/未知混合、11/15边界、用户最多与系统默认上限冲突、解释与表格对应；普通案例作保留对照。不优先继续增加城市。需先固定独立开发组合并证明可行，不能把验证答案直接变训练数据。
4. 若继续SFT，做受控数据消融：旧数据、旧+新城市、旧+上述定向难例，控制优化步数或明确样本暴露差异，使用同种子。先比较开发集配对变化和解释质量，再扩量。当前没有证据要求盲目延长epochs或增大学习率。
5. SFT稳定后再DPO。已有154对主要是开放/通勤，不能指望修复去重与天气。若构造新偏好，应只注入一种有证据的目标缺陷，两侧解释均忠实于各自路线，避免仅凭“错误解释风格”区分；基于最终选定SFT重新训练适配器与参考。当前未启动DPO。
6. 最终模型/协议冻结后再用丽江、景德镇留出测试跑四组实验；已有API原始记录保存，但新prompt/协议下若要比较必须同版本，历史API不能直接混算。
