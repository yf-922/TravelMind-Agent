# 旅行知识库定位与主链路检查

检查日期：2026-10-08。结论来自源码与离线检索，不是线上效果或 RAG 收益实验。

## 已确认的接入断点

`app/planning/graph.py` 的 `_planner_for_graph` 正常返回 `make_joint_planner_node`。联合 Planner 同时安排景点和餐馆，但没有调用知识检索，也没有把本轮检索来源写回状态。旧 `make_planner_node` 才调用 `search_travel_knowledge`、把片段加入提示词并返回 `rag_sources`。

现有 RAG Planner 注入测试直接调用旧 Planner，不能证明默认主图已经接入 RAG。最终输出将 `rag_sources` 复制为 `knowledge_sources`，并不保证来源是联合 Planner 当前使用的证据。

运行时知识库实际加载 `knowledge/travel/*.md`：3 篇文档、3 块内容，分别为重庆参考、可靠出行清单、交通与节奏指引。它们主要是项目建议和规划规则，缺少带官方来源的具体景点知识。

128 块、六城市语料属于独立的评测路径，不被该运行时加载。固定 BGE 的开发评测成绩不能直接称为当前产品 RAG 效果；运行时 Chroma 没有在此模块显式绑定已评测的 BGE revision。

## 应分开的四类信息

| 信息 | 归属 | 作用 |
| --- | --- | --- |
| 景点坐标、天气、道路耗时、当前营业与票务 | POI、地图、天气、官方页面或票务查询工具 | 当前可行性核验；票务接口并非已实现 |
| 展陈主题、景区区域与产品组成、稳定游览方式 | 有来源的旅行知识库 | 补充候选景点的语义信息，帮助 Planner 选点与组合 |
| 景点不能越界、日期时间与重复检查、当前需求优先 | 提示词与确定性规则 | 不应依赖能否召回某个规则片段 |
| 用户预算、兴趣、历史选择 | 用户 SQLite/语义记忆 | 个性化，不混入公共旅行知识 |

知识库可以保存官方预约入口和产品结构，但价格、名额、临时闭馆与预约政策须标记采集时间和适用日期；不能以旧快照代替实时核实。实时失败应明确待确认，不编造结果。

## 建议优先收录的内容

1. **展陈与活动内容**：哪些主题、展区、游览活动适合用户明确兴趣。需要官方展馆介绍或导览依据。
2. **空间与游览方式**：区域、入口与游览线路的说明。地图负责实际道路距离；知识库不承诺通勤时长。
3. **活动强度的可验证依据**：官方说明的阶梯、徒步路段或活动条件，而非“适合所有老人”这类笼统体验判断。
4. **产品组成与官方办理入口**：门票、索道、接驳车、专项预约分别是什么；当前价格和名额另查。

不扩展泛泛的带伞、放慢节奏、休息、优惠资格或陪护建议。此前“仅预约门票”方案保留为方向调整历史，不再作为本阶段有效设计。

## 先做哪些实现

1. 建立有城市、明确 POI/场馆、主题、来源 URL、采集与适用时间的语料；先补少量可靠景点介绍，验证用途，再扩数量。
2. 用用户兴趣及候选 POI 名称形成检索输入，限制城市与实体。检索只补充已核验候选，不能把召回文本里的景点直接加入候选池。
3. 将检索接入实际联合 Planner，统一旧 Planner 的注入格式；区分来源事实与不可信指令，检索失败不阻断基本规划。
4. 增加主图使用的联合 Planner 契约测试：检索内容确实进入提示词、候选边界保留、本轮无结果时旧来源不残留。
5. 对同一候选池、用户输入与模型比较有无 RAG。先测兴趣相关的选点依据、证据支持与未知事实处理，再测最终路线质量、Token 和耗时。没有完成实验前不声称提升。
